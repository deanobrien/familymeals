# Decisions

## D1 Monorepo: pnpm workspaces + Turborepo (2026-10-19)

Per BRIEF-REVIEW: enables parallel lanes and later Expo reuse of shared packages. Workspaces: `apps/*`, `packages/*`, `e2e`.

## D2 Scope `@fr/*`

Short for Family Recipes; neutral to the still-undecided product name, so a rename never touches imports.

## D3 Packages export TS source, no emit

`main`/`exports` point at `src/index.ts`; web uses `transpilePackages`; package `build` is a `tsc` type-check. Avoids build-order coupling in dev and keeps lanes independent. Revisit if a package must be published or consumed by a non-bundler.

## D4 Supabase config at repo-root `supabase/`

The CLI default location, so `supabase start` / `db push` work with no flags. `packages/db` holds generated types and helpers only. Migrations live in `supabase/migrations`, timestamped; later lanes add lane-named migrations. The baseline migration enables `pgcrypto` only; the schema is lane L1.

Modes: local stack (`supabase start`, needs Docker; Docker 20.10 on the TFS box may be too old) and cloud (London eu-west-2, `supabase link` + `db push`).

## D5 Test stack

Vitest per package/app (run through turbo), Playwright in `e2e/` (Chromium; starts the web dev server on port 3100), pgTAP/SQL tests for RLS later (L6). ESLint 9 flat config with typescript-eslint (no eslint-config-next yet; lane L2 may add it). Prettier: single quotes, 100 columns. The `@fr/e2e` script is named `e2e` so `turbo run test` does not launch Playwright.

## D6 Env handling

All variables are server-only (no `NEXT_PUBLIC_`). `AI_PROVIDER=mock` by default. `.env*` is git-ignored except `.env.example`.

## D7 Dev server port 3100

Avoids clashing with other local apps on 3000.

Planner mapping: lunch/dinner recipes are interchangeable main meals, `quick` tag when total time <= 30 min, cost per serving null when unknown; demo favourites = library favourites. ## D34 Receipts and the shared price store

## D60 Real cost and nutrition: one server-only calc module (lane C1)

`apps/web/lib/server/calc/` (`import 'server-only'`) replaces the placeholder seed values. `costRecipe` = `@fr/engine/cost` over refdata generic prices (`@fr/refdata/prices.json`) plus household observations from an injected `PriceSource` (`observations()` + `version()`; the engine ranks user_confirmed > receipt > retailer_verified > generic_estimate, so household prices win automatically); `nutritionForRecipe` = `@fr/engine/nutrition` over per-100g CoFID profiles (`@fr/refdata/cofid.json`, linked through each ingredient's `cofid.code`; a `proxy` mapping marks every value an estimate). `createRecipeCalculator` caches the full result per recipe VERSION (id + `updatedAt` + servings + price-source version), so an edit recomputes and a price change invalidates. `@fr/refdata` gained `./prices.json` and `./cofid.json` exports (JSON imports, no fs, like D28); a drift test compares prices.json with `loadSeed()`. ## D61 Nutrition policy

Per serving = recipe total / recipe servings. Unknown never becomes 0: an ingredient without a CoFID profile, or one whose weight cannot be resolved, makes every dependent nutrient `unknown` with the sum of the known parts only as `lowerBound` (shown as a note, never as the value). Non-optional "to taste" lines are treated as negligible (engine `treatToTasteAsNegligible`, reported in `warnings`) so salt/pepper do not blank every recipe; ranges use the midpoint, unit-weight and bracketed/proxy CoFID values are flagged `estimate`. The detail page scales ingredients with the servings stepper, so per-serving values stay constant and the per-recipe tab = per-serving x chosen servings. The page always shows "Estimated from UK CoFID data (...)" and the engine `NUTRITION_DISCLAIMER`; coverage % and the list of ingredients without data are shown.

## D62 Cost labelling and partial costs

The cost figure is the sum of PRICED lines only. When any non-optional line cannot be priced the result is `isPartial` and every surface says "At least": detail page ("At least £x per serving", "partial" badge, "n of m ingredients priced", uncosted lines listed with reasons), planner slot, week cost label ("... N meals with unpriced ingredients") and recipe search. The whole figure is labelled with the LEAST trusted price kind used (`generic_estimate` -> "estimate") and the price source and date are printed. Nothing priceable at all = unknown (null), never 0. `RecipeCost.partial` carries the flag on `RecipeView`. Known weakness: library sort-by-cost and price bands rank by the (possibly partial) lower bound, so a recipe with a missing price can look cheaper than it is; the card does not show the partial flag yet (needs a `@fr/ui` `RecipeCard` prop).

## D63 Cost and nutrition are derived, not stored; seed placeholders removed

`RecipeView.cost` / `nutritionPerServing` are no longer stored or seeded. `InMemoryRecipeRepository` takes an optional `RecipeSummariser` (the server factory injects the calculator) and fills both fields on every read (`view()`), so list sort/filter/price bands, `get`, `create`, `update` and `duplicate` always reflect the current recipe version and prices; with no summariser (unit tests of other lanes, import pipeline tests) cost is null and nutrition empty. `seed.ts` lost `totalPence`/`nutrition` enrichment and the fake nutrient rows; fixtures are untouched. Specs and tests asserting placeholder numbers (0.95/5.70, "Cost unknown" for the flapjacks recipe) now assert computed values or the partial/unknown behaviour.

## D64 Planner: computed costs and weekly nutrition

`RepositoryPlanRecipeSource` takes an optional `nutritionOf` (calc `nutritionPerServing`); `PlanRecipe`/`RecipeLite` carry `costPartial` and the per-serving `NutrientMap`. `weekCost` counts partial meals and says "At least". `lib/plan/nutrition.ts` runs the engine `summariseWeek` client-side over the page's recipes, so the new "Nutrition this week" panel (`app/plan/week-nutrition.tsx`) updates live as the grid changes: week total, average per planned day and average per serving, `Unknown` where any meal lacks data, count of meals without nutrition, the engine disclaimer constant, no targets or adequacy language. Eating-out and leftovers meals are excluded. `loadFixtureRecipes` (fixture-backed `InMemoryPlanRecipeSource`, unit tests only) keeps its demo costs.

## D65 Printed card nutrition shown beside the calculation

When a `RecipeView` has `printedNutrition` (`PrintedNutritionView`, added by the import lane), the nutrition panel adds a separate "From the recipe card" column on the per-serving table (printed names mapped to our nutrients, unmapped rows appended, kJ ignored), states the printed basis and note, and labels the figures source-provided, not calculated by this app and not scaled (`data-testid="printed-nutrition"`). No printed data = column skipped. The per-recipe tab never shows printed values. Printed allergens render under the panels (`printed-allergens`). The merge with the import lane replaced its inline printed block in `RecipeDetail` with this column; its e2e test ids are kept.

## D52 Recipe mapping decisions

## D71 Shopping sync = the L17a engine client model over the command log

`@fr/mobile` now depends on `@fr/engine` (subpaths `./shopping`, `./units`; the D32 "engine not added" note is superseded). Per household the data source holds the engine `ClientState`: `confirmed` (snapshot + replayed log) at `cursor`, ordered `pending`, optimistic view = pending over confirmed (`clientView`/`deriveAll`). Snapshot = `shopping_list_items` + `purchase_events` with the cursor (max `shopping_command_log.seq`) read BEFORE the rows. Catch-up = `shopping_command_log` rows with `seq > cursor` mapped to engine `LogEntry`s (`tick`/`purchase`/`void` -> tick/purchase/undo) and ingested with `clientIngest`. Anything it cannot replay (add/edit/remove/regenerate entries, a seq gap, a full page of 500, or an applied purchase the engine replay did not reproduce) falls back to a fresh snapshot via `clientResync`, which keeps `pending`. Writes go only through `record_purchase` / `void_purchase` (client-generated command id = idempotency key; rejections are data). Ticks pass the engine's `expectedOutstanding` + `expectedEventCount` from `confirmed`; if the server answers `needs_engine_outstanding` it has already consumed that command id, so the client resnapshots and re-sends the tick ONCE under a new id (then reports a conflict). Realtime subscriptions are not used: resync happens on screen focus, app foreground, pull-to-refresh and reconnect.

## D72 Offline queue persistence and replay

`OfflineStore` (AsyncStorage) persists `pending` commands per household (`fr.shopping.v1.pending.<hh>`) and the last confirmed snapshot (`...snapshot.<hh>`, cache only) so a cold start with no signal shows the cached list with queued ticks applied. Corrupt entries are dropped, never thrown. NetInfo (`@react-native-community/netinfo`) feeds `AppProvider`: on offline -> `ds.setOnline(false)` (no delivery attempts, banner shown); on reconnect -> `ds.flushPending()` then a `syncVersion` bump so screens re-read and drain conflicts. Flush sends commands in order and stops at the first transient failure (no code / network / PGRST0xx / 5xx); acknowledged commands are dropped only after the log sync that folds them into `confirmed`, and a re-send after a lost response gets `duplicate: true` (counted as delivered, no double purchase). Final errors (e.g. `P0002` item gone) become a conflict, never an endless retry.

## D80 Pantry scan is one `@fr/ai` operation with a minimal context (P2)

`scanPantry(images[], context, ctx)` (new `packages/ai/src/pantry-scan.ts`; wired once in `BaseAiProvider`, so OpenAI, Azure OpenAI, Anthropic and the mock all carry it; `createResolvingProvider` forwards it; usage operation `scanPantry`). It accepts up to `SCAN_MAX_IMAGES` = 10 images (the recipe flow keeps its limit of 6). Per item: `name`, `form` (fresh | chilled | frozen | canned | dried | ambient | other), `packaging` (loose | pack | tin | jar | bag | bottle), `count` (individual items if loose, packs otherwise), `packSizeText` as printed plus `packSize {value, unit}` per pack (only when legible), `dates {useBy?, bestBefore?, legible, needsCloseUp}`, `confidence`, `frameRefs` (1-based images it appears in), `notes`. ## D81 Scan output is sanitised in code, not trusted

`normaliseScan` (in `pantry-scan.ts`, applied by `BaseAiProvider.scanPantry` and the mock): dates are dropped whenever an item is flagged not legible or needs a close-up, impossible calendar dates are dropped, `needsCloseUp` is never kept beside a date, `legible` is recomputed from whether a date actually remains, frame references are clamped to the images actually sent (default `[1]`), names are trimmed (empty ones dropped), and a pack size without its printed text is ignored. Items are NOT merged in code: de-duplication is the model's job and every downstream step tolerates repeats (rows for the same ingredient and date merge through the engine's `addStock`). The mock reads `fixtures/pantry-scan.json` with relative dates (`+2d`) resolved against `context.today`; a `focusItem` close-up returns that single item with a readable use-by so the close-up flow is testable.

## D82 Video is turned into frames in the browser; only JPEG frames are uploaded

`/pantry/scan` accepts `image/*` (gallery or camera) and `video/*` with `capture`. A video never leaves the device: `lib/pantry/video-frames.ts` seeks a `<video>`, draws to a canvas and keeps 6-10 frames (about one per 1.5 s, `chooseFrameCount`). `lib/pantry/frames.ts` (pure, pixel arrays in) splits the clip into equal windows (skipping the first/last 3%), samples 3 candidate times per window and keeps the sharpest by variance of the Laplacian on a 160 px grayscale copy, so frames are spread across the whole clip and each is the least-blurred of its neighbourhood. Clips with no duration metadata (MediaRecorder output) are handled by seeking far to force one. The chosen frames show as numbered thumbnails (removable) before sending; photos and frames share the 10-image cap. The UI says dates read best from close-up photos.

## D83 Scan endpoint is read-only; rows are matched with the engine's conservative matcher

## D84 Nothing is written before confirm; preview and confirm share one engine function

Review rows live only in the browser. `previewScanAction` (read-only) and `confirmScanAction` both call `planScanAdditions` (`lib/pantry/scan-apply.ts`), which runs the engine's `addStock` row by row over a copy of the household's stock, so the "merge with existing stock" preview (before -> after for a merge, "new line" otherwise, with a note when an existing line is kept separate because of a different date or older stock) cannot disagree with what confirm writes. ## D85 One pantry expiry: use by wins over best before

## D86 Default quantity from count and pack size

## D121 Per-list cursor and log replay

`shopping_command_log.list_seq` is a per-list, gap-free sequence assigned by a BEFORE INSERT trigger through a counter row (`shopping_list_log_heads`) that stays locked until commit, so `list_seq` order = commit order and a reader never sees k+1 without k (the global identity `seq` can commit out of order and is shared by all lists, so it cannot be an engine cursor). Every writer takes the counter last (no lock-order cycle). Log rows map back to engine `LogEntry`s: engine-written rows carry the engine command/result; `record_purchase` rows map tick -> `purchase` of exactly the recorded quantity (an unquantified tick stays `tick`), void -> `undo`, rejections keep the SQL reason (`needs_engine_outstanding` -> the new engine reason `superseded`, `invalid_price` -> `invalid_quantity`); the logged actor (session user) always wins. `@fr/engine/shopping` change: `applyLogEntry`, a REJECTED log entry is authoritative on replay (outcome recorded, state untouched) and applied entries are re-run; identical for the in-memory server (engine shopping tests incl. the 200-case fuzz pass). After `needs_engine_outstanding` (SQL could not convert and our expected values went stale) the server re-decides from a fresh snapshot under a derived id (`tickRetryId`, up to 3 times); an undo of the original id is redirected to the derived event; the client never shows `superseded`.

## D183 Mapping rules: missing is not zero

`mapOffProduct` (packages/product-sources/src/off/map.ts): nutrition is per 100 g, or per 100 ml for liquids (flagged `per: 'ml'`). A nutriment absent from the record is `unknown` (no value), never 0; only an explicit 0 is `zero`; negative or non-numeric values are ignored. Sodium is converted g -> mg. Missing salt is derived from sodium (x2.5), missing sodium from salt, missing kcal from kJ (and the reverse); derived values are listed in `nutrition.derived` and marked `estimate`. A block whose protein+carbohydrate+fat+fibre+salt exceeds 105 g/100 g, or energy above 950 kcal/100 g, is WITHHELD with a reason (crowd-sourced entries are sometimes whole-pack or per-serving). Allergens map onto the UK-14 groups (`en:gluten` -> cereals_gluten, `en:nuts` -> tree_nuts, `en:soybeans` -> soya, `en:sesame-seeds` -> sesame, `en:sulphur-dioxide-and-sulphites` -> sulphites, ...); tags that do not map are kept in `unmapped`. NO allergen data (no allergen tags and no ingredients text) is `status: 'unknown'` and is always shown as "check the pack": absence is never presented as allergen free. Pack size comes from `quantity` text via the engine parser ("400 g (drained 240 g)" = 400 g, "6 x 125 g" = 750 g with `packCount` 6, "75cl" = 750 ml), with `product_quantity` as a fallback and no invented value otherwise. The canonical-ingredient suggestion uses EXACT name/alias matches only (generic name, product name minus brand, then category tags most-specific first); an ambiguous match is returned as candidates and never pre-selected.

## D265 Merge rules (SL1)

## D200 RT1: "live" means the postgres_changes listener is server-confirmed, not "channel joined"

LV1 found that `createSupabaseLiveFeed` reported `live` at the channel's `SUBSCRIBED` status, slightly before the server activates the `postgres_changes` listener (it confirms with a realtime `system` message, `extension: 'postgres_changes', status: 'ok'`). The controller stopped polling at that point, so a row committed in the gap was delivered to nobody and waited for the next sync. Now `SUBSCRIBED` only arms a confirm timer (10 s; unconfirmed -> tear down, backoff, retry); the feed reports `live` on the `ok` system message, and a non-ok postgres_changes system message is a failure (down + retry). The controller keeps polling until `live`. `ControllerState.live` / `data-live` on `shopping-root` expose it for tests. Consistency with Android (M3, D211, `apps/mobile/src/data/liveFeed.ts`): same confirmation rule; the one deliberate difference is that Android reports live after 5 s without confirmation, web instead retries and keeps polling (never claims live unconfirmed). Android could adopt the web second catch-up (+1.5 s) later.

## D201 RT1: two cursor catch-ups after every confirmation; duplicate application is impossible

On every transition to `live` (first connect and every resubscribe) the controller syncs from its cursor immediately (anything committed before the listener existed) and again after `CATCHUP_AGAIN_MS` (1.5 s, closes the race with a commit that landed while the confirmation was in flight). Both are plain `sync()`s: cursor-based, serialised, and `clientIngest` ignores entries at or below the cursor, so overlapping catch-ups, events and polls apply each log row exactly once (unit-tested). Going down cancels the pending second catch-up and resumes the 4 s poll.

## D202 RT1: heartbeat, tab sleep/resume, offline->online

While live the feed emits a catch-up hint every 30 s (heartbeat); a heartbeat gap above 2.5x the interval means the tab or laptop slept, so it reconnects immediately (no backoff) because the socket is probably dead. `online` and tab-visible events reconnect immediately if the feed is down and otherwise request a catch-up. Reconnects always go back through D200 (confirmed before live) and D201 (two catch-ups).

## D203 RT1: token refresh

## D210 Android shopping sync uses the per-list `list_seq` cursor and the snapshot RPC (M3)

`SupabaseDataSource` no longer uses the global `shopping_command_log.seq` (it commits out of order and is not contiguous per list, so it was never a valid engine cursor: gaps meant resnapshots). It now mirrors the web Supabase repository: the snapshot is `shopping_list_snapshot(p_household_id)` (items with engine state, events and the log in one statement; `head` = the cursor, log rows seed the idempotency outcomes), catch-up reads `shopping_command_log` with `list_seq > cursor` for the active list, and `src/data/shoppingMapping.ts` is a port of the web `logRowToEntry` / `itemFromRow` / `stateFromSnapshot` (so engine-written commands from the web, e.g. add/edit/remove/regenerate, now replay on the phone instead of forcing a resnapshot). Each catch-up also checks the household's active list id and rebuilds from a snapshot when it changed. Concurrent loads and syncs are coalesced (the list screen, the live feed and a reconnect flush used to be able to race). Persisted state is per list (`fr.shopping.v2.list.<listId>` = confirmed state + `list_seq` cursor, `fr.shopping.v2.active.<householdId>` = pointer + member names); a cold start resumes from that cursor with a log catch-up instead of a full read, and offline it uses the cache with no network call. One behavioural change this forced: the snapshot's log now contains the REJECTION `record_purchase` logs for `needs_engine_outstanding`, and the engine drops (and reports) a pending command whose id already has a rejected outcome. The re-issue path therefore swaps the pending command to its new id BEFORE re-reading the snapshot; the old order made the retried tick vanish silently.

## D221 Resolution rules on save (server-side, `saveRecipeAction`)

## D271 Decoder: platform BarcodeDetector, else lazy zxing-wasm (replaces the "no library" part of D189)

Evaluated: `zxing-wasm` 3.1.6 (MIT, maintained, published 2026-10-19; reader-only build), `@undecaf/zbar-wasm` 0.11.0 (LGPL-2.1+, 3.3 MB unpacked, last release 2024-05), `barcode-detector` ponyfill (MIT, a BarcodeDetector shim over zxing-wasm that fetches its wasm from a CDN by default, which our CSP forbids), zxing-js (unmaintained). Chosen: `zxing-wasm/reader`. Cost: `zxing_reader.wasm` is 946,860 bytes raw (about 410 kB gzip) plus a ~53 kB JS loader, BOTH fetched only when the scanner starts on a browser without a usable BarcodeDetector (iPhone Safari, Firefox, desktop); where `BarcodeDetector.getSupportedFormats()` includes `ean_13` (Android Chrome) nothing is downloaded. The wasm is committed at `apps/web/public/vendor/zxing/zxing_reader.wasm` (self-hosted, no CDN; `.gitattributes` marks `*.wasm` binary; a unit test asserts its SHA-256 equals the installed package's `ZXING_WASM_SHA256`, so an upgrade that forgets to re-copy it fails). Production CSP `script-src` gains `'wasm-unsafe-eval'` (needed to compile WebAssembly; it does not allow `eval`); middleware lets `.wasm` through the matcher. Formats: EAN-13, EAN-8, UPC-A (normalised to EAN-13), UPC-E (expanded to UPC-A first: it is the only format where an 8-digit code is not an EAN-8). Check digits are always verified. Measured in Node over a 640x320 noise frame (worst case, nothing to find): 1.5 ms per frame without `tryHarder`, 4.9 ms with; rendered EAN-13/EAN-8/UPC-A frames and 2 px-module barcodes decode in unit tests. A native detector that throws `NotSupportedError` hands over to the wasm reader for the rest of the session; `?decoder=wasm|native` forces one (used by e2e). Needs real-device verification: speed and autofocus on mid-range Android and iPhone.

## D272 Lookups never block scanning: batch endpoint, per-household queue, cache (`lib/server/products/batch.ts`)

`POST /api/products { codes[<=50], retry?, householdId? }` (web cookie or Android bearer; JSON only; read-only) answers at once with a status per code: `done` / `notfound` / `pending` / `error`. Resolution order: the in-process LRU of recent lookups (500 entries, 24 h hits, 1 h misses; public product data only, nothing about any household, so D182 is unaffected), then the household's own product snapshots (D187; the product they confirmed, matched to the ingredient they linked), then a per-household FIFO queue drained by ONE worker that round-robins between households and calls the existing `lookupProduct` (so the source's own limiter, 10 reads/min, D181, still sets the pace, below Open Food Facts' 15/min, D180). A retryable `rate_limited` answer is waited out (6 s, up to 12 tries) instead of failing the product. At most 120 queued per household; a polling-rate guard (150 requests/min/household) is separate from the upstream allowance. Failed codes stay failed for 30 s unless the client sends `retry`. The client (`createLookupTracker`, engine) requests each distinct code once, polls only the still-pending codes every 1.5 s in chunks of 25, and backs off on network errors. Consequences: 40 never-seen products take about 4 minutes to resolve fully at 10/min, but scanning and review are not blocked, rows fill in as they land, and any row can be named by hand meanwhile; repeat shops resolve instantly from snapshots. State is in process memory (App Service single instance); with several instances each has its own queue and the per-IP upstream limit is shared (same caveat as D181).

## D273 Tally semantics: counted once while held, again after moving away

A read is counted when the code is new, or when its last COUNTED read was at least 1.5 s ago AND it was out of view for at least 0.5 s. Holding a pack in front of the camera therefore counts once however long it stays, moving away and back counts again, and a pack swapped back within 1.5 s is ignored (the + button covers a fast same-product run). Typed digits always count. Undo reverses the last change (scan, +/-, removal) and clears that code's cool-down so the same pack can be scanned again straight away. Caps: 99 per product, 150 distinct products. Rows whose lookup is `pending` block confirm (a clear message, and "Name it myself" unblocks them); `notfound` / failed rows ask for a name or an ingredient; a row the owner named is never overwritten by a late lookup.

## D250 Data export is built on demand and streamed; nothing is stored (DX1)

## D251 Own streaming zip writer, SHA-256 manifest (DX1)

## D253 Account deletion: leave now, delete later, by the job (DX1)

## D256 `/api/jobs/purge`: one idempotent endpoint behind JOBS_SECRET (DX1)

## D371 SSRF guard (P1-B)

## D390 Store location is a point and a radius saved per store; a live position is never stored (P2-A)

## D391 Two ways to set a location, neither needs a map; postcodes.io for the lookup (P2-A)

## D392 Detection is pure and on the device (P2-A)

The same module runs in the browser and on the phone; the live position is compared there and goes nowhere. ## D393 Android: opt-in, foreground and optional background geofences (P2-A)

If background permission is refused the app stays foreground-only and says how to allow it. On arrival the shopping screen switches "Shopping at" (and with it the aisle order); a background arrival is recorded on the device and applied once, if it is under 30 minutes old. Optional nudge "You're near Tesco - 6 items on your list": a LOCAL notification on the existing `default` channel, never sent by the server, gated by a new notification type `near_store` that is off by default (migration `20261021002010` only makes the type valid so the member's choice can be saved). The count comes from the last list the phone showed (cached on the device); when unknown it says "Open your shopping list" rather than guessing. "Turn off and erase" and sign-out stop the geofences and delete everything this feature keeps on the phone (`fr:geo:*`). Chosen modules: `expo-location ~58.0.18`, `expo-task-manager ~58.0.12`. ## D394 Why geofences carry coordinates only on the device (P2-A)

The geofence regions are built on the phone from the saved store spots and registered with Android; the server never learns whether the phone entered one. The phone does not tell the server it is "at Tesco" either (the household activity feed does not mention it). The consequence is that other members cannot see where you are, which is the point.

## D395 Voice add: speech-to-text on the device, parsing on the server, review before adding (P2-A)

Mic button on the shopping list (web: "Voice add"; Android: "Add by voice"). Web uses the Web Speech API where it exists (Chromium and Safari; the browser's speech service handles the audio, which the UI says plainly); Android uses `expo-speech-recognition 58.0.0` (MIT, peer `expo *`, Android SpeechRecognizer, the SDK 58 release published for this SDK; adds `RECORD_AUDIO`, already declared). Both fall back to typing, which uses the same box. The text goes to `POST /api/shopping/voice/parse`, which reads it with the engine's `parseSpokenList` (lead-ins like "add" / "we need" and trailing "to the list" removed, split on commas / "and" / "then" / "also", protected phrases such as "fish and chips", then the existing `parseIngredientLine` for quantities, units and number words) and the same conservative catalogue matcher as the handwritten scan. It WRITES NOTHING; the member sees chips (tap to leave one out) and adds through the existing `/api/shopping/scan/confirm`, which is idempotent on `batchId`, so a double tap or a retry never adds twice. The transcript is never stored or logged; an empty or over-long (1200 characters) transcript is refused. Units outside the list's own are kept as a note, ranges use the larger number and say so.

## D396 Web: location only while the page is open, and why (P2-A)

The shopping page has "Detect my store" (one reading on a button press) and an opt-in "Detect automatically while this page is open" (a watch that stops when the page is hidden or closed, off by default, remembered per member per device in localStorage). Everything else (saved spots, radius, postcode lookup, the aisle switch) is the same on both.

## D400 Money tracking: no new price table; spend is receipts plus manual entries; all numbers computed on the server (P2-B)

Per-shop prices are the household's OWN `ingredient_prices` rows (`receipt` / `user_confirmed` with `retailer`), exactly what receipt confirmation already writes (D124): generic estimates and shared `retailer_verified` rows carry no shop and are ignored by comparison. Migration `20261021002100_p2b_money.sql` adds only `spend_entries` (spend entered by hand: date, pence, optional store or retailer text, category, note) and `store_retailer_links` (normalised receipt retailer text -> one of the household's `stores`), both plain household tables under RLS like AS1 (members read, members of a writable household write, composite FKs keep a row and its store in one household; deleting a store drops its links and clears the spend's store reference), plus the read function `household_spend_receipts(household, from, to)` (reconciled receipts with their lines in one round trip). Actual spend = confirmed (reconciled) receipts + manual entries, nothing else; a receipt still waiting for review is never counted. Pure maths is `@fr/engine/money` (time, unitprice, compare, listCompare, spend); `apps/web/lib/server/money/` gathers inputs and shapes view models (`SpendingView`, `ListCompareView`, `PriceHistoryView`); web pages, server actions and the bearer routes `/api/money/{spending,spending/csv,compare,prices}` all call the same services, and Android renders what the server returns (it never computes a price or a week itself).

## D401 Unit prices and "cheapest at": compare like with like, only recent prices, say how old (P2-B)

A pack price is normalised to pence per kg (any mass unit), per litre (any volume unit) or per item (counts); weight and volume are NEVER converted into each other (a shop price carries no density), so prices on different bases are listed but not ranked. A bare "1 item" pack (the receipt gave no size) is per pack and flagged `packSizeKnown: false`. Each shop's LATEST observation is its current price (same day: a price you entered beats a receipt). A "cheapest at" call needs at least TWO shops with a price from the last 60 days on the same basis (the basis most shops share: kg, then litre, then item); older prices appear in the history and table but never rank. A tie is "joint cheapest", never a winner; the badge always carries the unit price and the age ("Cheapest at LIDL: £2.30 per kg (6 days ago)"); with one shop, old prices or mixed bases there is no badge and the history says why. `retailerKey` lower-cases, strips punctuation and words like Ltd/Stores, so "TESCO STORES LTD" and "Tesco" are one key.

## D402 "Where's cheapest for this list?" never pretends full coverage (P2-B)

Per shop: the cost of the outstanding list items that HAVE a price at that shop (same proportional costing as the basket, one price per item = that shop's latest), how many of the list's items that covers (`n of m`, %), the items not counted, and how old the oldest used price is. Shops are ordered by coverage first, then total, so a cheap total over three items cannot look like the winner. A separate like-for-like row totals only the items priced at EVERY listed shop and names the cheapest of those (or "no single cheapest" on a tie). With no or one shop the panel says so instead of showing a number. Copy says it is built from the household's own receipts and prices and is not a quote.

## D403 Linking receipts to stores needs a confirmation; text equal to a store name does not (P2-B)

`suggestStore` matches the receipt's retailer text to a store by whole-word name or chain ("TESCO EXTRA" -> Tesco); two equally good matches means no suggestion. A suggestion is only ever APPLIED when the user confirms ("Yes, link it" on the receipt review page or the Spending page; Android: same on Spending); the link is stored per retailer text, so every receipt and price with that spelling is counted as that store from then on, and Unlink removes it. The one exception needing no confirmation is text exactly equal to a store's name (a price entered "at Tesco" is the store Tesco). Unlinked retailers still compare, as their own shop under the printed name (labelled "not linked to a store"). Store locations from P2-A are not used: the printed name is the signal, a saved location says where a shop is, not which shop a receipt came from.

## D404 Budget tracking: three different things, never blended (P2-B)

Per week: the household's weekly budget (the current setting, applied to every week: a history of budget changes is not kept, and the page says so), the PLANNED figure (cost of the APPROVED plan from recipe costs: an estimate, "at least" when some meals or ingredients are unpriced, absent when there is no approved plan; drafts do not count) and the ACTUAL spend. Statuses are worded and iconed, never colour only: over budget is over even mid-week; a week still in progress is "so far" / "left so far" and never "under budget"; a plan estimate that is only a lower bound but already above the budget is "over", a lower bound below it is "unknown", never "within". No budget set is stated ("Not set"), not treated as zero. The variance against the plan is only shown when the plan figure is not partial. Leftover, freezer and eating-out slots (P2-C, D417) need no shopping, so they add ZERO new spend to the planned estimate: they are not "unknown" and never make it partial; a plan week of only such slots is an estimate of £0 (`plannedWeekFor`, unit tested). Only recipe meals with no price make the figure "at least" or unknown.

## D405 Weeks and months in Europe/London; charts (P2-B)

A week is Monday to Sunday as the planner already uses. Instants (a receipt with no printed date, "today") become a calendar date through `Intl` in Europe/London, so 23:30 UTC on a BST Sunday is Monday 00:30 in the new week and 23:30 GMT on a winter Sunday stays in the old one; date arithmetic is done on UTC midnights so a clock change cannot shift a week (unit tests cover both changes, 2026-03-29 and 2026-10-25). Monthly rows are the weekly rows grouped by the month each week STARTS in, so budget, planned and actual always use the same weeks (no pro-rating; said on the page). The chart (web SVG, Android bars) has one pounds axis; actual = solid, planned estimate = hatched/dashed, budget = a dashed tick/line, a legend, a table view of the same numbers and a spoken sentence per row, tokens from the design system so dark mode works; palette validation is not needed (two fills told apart by pattern, plus a line). Category breakdown uses the shopping list's own aisle categories: receipt lines are matched to the catalogue by exact name only, everything else and any remainder is "Uncategorised" (splits are always normalised to add up exactly to the total; lines adding up to more than the printed total are scaled down).

## D410 Calendar-aware planning: three sources, one rule, derived flags only (P2-C)

Busy evenings come from (a) a manual "Busy" toggle per day in the planner (web and Android, always available, any member), (b) the Android phone calendar and (c) an ICS subscription read by the server. All three end as rows of `plan_busy_days` (migration `20261021002200`): household, day, source (manual / device / ics), the member, and `minutes_available` (free minutes in the evening window, null for a manual toggle). Nothing else is stored anywhere: no event title, place, notes or attendee exists in the schema, the reader, the wire format or the export. Flags are household-visible (everyone planning needs them); a member's device / ics rows are deletable only by that member, manual toggles by anyone writable; a member who leaves takes their device / ics flags and feed with them (trigger).

## D411 Busy-window derivation (P2-C)

`@fr/engine/calendar` (`deriveBusyDays`) is pure and runs ON THE PHONE for Android and on the server for ICS: events are reduced to start / end / all-day / busy, clipped to the local 17:00-20:00 window (converted to instants per day, so the 29 Mar and 25 Oct clock changes are exact, in the stated IANA zone), overlapping events are merged (counted once), and a day is busy when 60 or more window minutes are taken; `minutesAvailable` is what is left. Free / transparent and cancelled events are ignored; tentative counts as busy. ALL-DAY EVENTS NEVER MAKE AN EVENING BUSY (they have no time of day: birthdays, bank holidays, "working from home"), a documented limit; use the manual toggle for those days. A multi-day timed event busies each evening it spans.

## D412 The ICS reader (P2-C)

`parseIcs` reads only DTSTART, DTEND, DURATION, RRULE, EXDATE, RECURRENCE-ID, UID, STATUS, TRANSP and Outlook's busy-status, so a title cannot leak from it by construction (a test feeds it SUMMARY / LOCATION / ATTENDEE text and asserts the output has four keys). It handles UTC, TZID, floating and date-only values, Windows zone names (a small map; an unknown name falls back to the member's zone), line folding, and recurrence in the event's own zone (DAILY / WEEKLY with BYDAY / MONTHLY by month day or nth weekday / YEARLY, INTERVAL, COUNT, UNTIL, EXDATE, moved instances). Limits: 4 MB of text, 20 000 events, 20 000 generated candidates per series (counted from the series start so a daily event from years ago still reaches today; far-past candidates are counted, not converted); anything it cannot read is skipped and only counted. The feed is fetched with P1-B's `guardedGet` (new `expect: 'calendar'`: text/calendar, text/plain, octet-stream): scheme / port / name checks, every DNS answer public, connection pinned to the checked address, every redirect hop re-checked, size and time bounded, no cookies. `webcal://` is rewritten to https. Offline e2e uses a fixture feed on the same fixture host (`URL_IMPORT_SOURCE=mock`).

## D413 How busy days reach the solver (P2-C)

The orchestrator takes a `busy` dependency (server-resolved, so it stays free of the engine): for the plan's dates it returns quick dates, skip dates and the applied days. They are re-imposed on every solve exactly like household exclusions (the request cannot remove them; change them with the Busy buttons or the calendar settings): busy dates are unioned into `quickMeals.dates` keeping the request's own minutes and strictness (default 30 min, soft); an evening with fewer than 20 free minutes becomes a `skip` of the DINNER slot (reason other, note "Busy evening"). `quickMeals` applies to every planned meal on that date (the solver has no per-meal-type quick rule; changing that would alter the AI-facing schema), skip is dinner only. The parse step returns the week's busy days and the proposal returns `busyApplied`; both are shown as chips ("Wed 21 Oct: Busy (about 45 min free) (phone calendar)"). A busy-flag failure never blocks a plan.

## D414 Android phone calendar (P2-C)

`expo-calendar` (~58.0.6), opt-in in Settings > Calendar and busy evenings (`CalendarSettingsScreen`), off by default, nothing is read before the switch is turned on and the Android permission (READ_CALENDAR, with the explanation text) is granted. `toEvent` is the only place a device event is read and it touches neither title, notes, location nor attendees; `deriveDevicePayload` computes the window on the phone with the shared engine; `POST /api/calendar {action: device_sync}` accepts only `{date, busy, minutesAvailable}` per day (validated: ISO dates inside the range, 0-1440 minutes, no duplicates, extra fields ignored) and replaces the member's own device flags in that range. The planner syncs (best effort, 4 s cap) when it opens if the member opted in. Switching off calls `device_revoke` (deletes the member's device flags) and clears the opt-in. Android version stays 0.3.0 / versionCode 3 (shared with P2-A: the new native module needs a new EAS build; the OTA runtime policy keeps this JS off older binaries).

## D415 ICS address: secret handling and privacy surfaces (P2-C)

The address is a bearer secret (anyone holding it can read the calendar). It is validated, proven by a first fetch (nothing is saved if the fetch fails), then stored AES-256-GCM encrypted with APP_SECRET, bound to household + member as AAD (`member_calendar_feeds.url_encrypted`, one row per member, RLS own row only, even other members cannot select it). It is never returned by any route or action (status shows the host name only), never logged (fetch failures log the error class name only; a test asserts the token and host never reach console output) and never exported (the export keeps the row's host, sync time and status, and the `encrypted` column rule drops the ciphertext, so the export says that a link exists). Refresh is throttled (5 minutes per member) and, on planner page loads, only when the last read is over 6 hours old. Unlinking deletes the address and the member's ics flags. Privacy notice (web page, PRIVACY.md) and the data export (`calendar.json`, `leftovers.json`) cover busy flags, the link's presence and the leftover ledger.

## D416 Leftover batches and the portion ledger (P2-C)

`leftover_batches` (title, portions made, fridge / freezer, cooked on, use-by; migration `20261021002210`) and `leftover_consumptions` (batch, idempotency key, portions, eaten / discarded). Portions are never a stored balance: left = made minus the ledger (`@fr/engine/leftovers`), a consumption key is unique per batch, and a trigger refuses to take more than remain (row lock). The batch is a household list shown in the Pantry as "Leftovers and freezer" (the pantry's engine items stay untouched: no change to `replace_pantry_items`, restock, "what can I make" or the expiry job, and no new unit); the existing ad-hoc "Cooked a batch today?" suggester stays as it was. "Cook x2 / batch" on mark-cooked (web form and Android form; `batch: {multiplier 2-6, storedIn}` on the existing cooked route): spare portions = servings x (multiplier - 1), one batch per cooked event (`source_key = cooked:<id>`, unique), so a retry or double tap cannot make two. A failure to record the batch never un-saves the cook.

## D417 Leftover and freezer meals in plan slots (P2-C)

A plan slot of kind `leftovers` may carry `batchId` + `portions` (`planned_meals.leftover_batch_id`, servings = portions; `save_meal_plan` redefined in `20261021002210`, deleting a batch turns its slots back into plain "leftovers" slots). It is not a recipe entry, so cost, nutrition, variety and the shopping requirements never see it (an e2e / server test generates the list from a plan with a freezer meal and finds no requirement). Save and approve re-check on the server: the batch exists, 1-100 portions, a fridge batch is not planned after its use-by, and the batch's portions already promised to other unconsumed slots (this plan and other weeks) plus this slot do not exceed what is left. "Mark eaten" (`/api/leftovers action eaten`, web button, Android button; needs a saved plan) takes the slot's portions once with the key `plan:<planId>|<date>|<mealType>`: a second tap or replay applies nothing and an eaten slot stops counting as promised, so nothing is double counted. Recipe slots have no "eaten" step (cooking them already has its own history).

## D418 Defaults and suggestions (P2-C)

Use-by defaults: 2 days in the fridge, 3 calendar months in the freezer (month ends clamp), counted from the day stored; "Move to freezer" is allowed only while the fridge use-by has not passed and restarts the 3 months from today. `suggestLeftoverSlots` offers only portions not eaten or already planned: fridge batches first (soonest use-by, never past it), then freezer batches with busy evenings first, one suggestion per open dinner / lunch slot (never snacks, never past days), labelled "Freezer meal: Chilli, 2 portions" or "Leftovers: Chilli, 2 portions (use by Fri 23 Oct)" with the reason ("A busy evening: nothing to cook"). A suggestion is only a button: it fills the slot as an unsaved edit like any other edit; nothing is planned silently and the solver does not place leftovers.

## D419 Parity, not built, and what was verified (P2-C)

Both platforms: Busy toggles, busy chips in the prompt flow and on the proposal, leftover / freezer picker, suggestions, mark eaten, portions stepper, Cook x2 on mark-cooked, the Pantry freezer view, the calendar link (web: planner "Calendar and busy evenings"; Android: Settings > Calendar) and the privacy text. Documented differences: the phone-calendar source is Android-only (a browser cannot read a calendar; web users link the calendar's ICS address instead, and a member who has both gets both merged); the address is typed or pasted on both, shown on neither afterwards. Not built: per-meal-type quick rule, calendar write-back, Outlook / Google OAuth (the ICS secret address covers both without an app registration), all-day events as busy, a "cooked it" step for recipe slots, push reminders to eat fridge leftovers (the expiry job does not know batches), partial-portion editing of a planned slot after it is eaten. Verified: engine (busy derivation incl. DST / all-day / overlap, ICS fixtures, leftovers ledger and suggestions), solver integration (busy becomes quick or skip), RLS + save_meal_plan on PGlite, routes and services (SSRF refusals, encryption, no logging, ledger idempotency), the web UI in Chromium, jest with a fake calendar. Not verified: the Android calendar permission prompt and a real calendar on a device, real Google / Outlook feeds, the hosted database.

## D441 The widget reads and ticks through the app's own data source (P3-C)

No second code path: a tap calls `DataSource.tickItem`, i.e. the SAME engine command (client-generated command id, idempotent replay, `record_purchase` RPC, persisted offline queue) as the shopping screen; undo is `undoTick`. While the app process is alive `AppProvider` registers its own data source with the widget bridge (`registerActiveSource`), so the widget shares ONE in-memory queue instead of racing it; with the process gone the headless task builds a standalone `SupabaseDataSource` over the same SecureStore session and the same AsyncStorage queue and snapshot cache. The app tells the widget which household is on screen (`setWidgetHousehold`, kept in `fr.widget.v1`) and redraws it after every shopping read, household change and reconnect replay. The periodic update first delivers ticks queued offline (`flushPending`), then reads; offline it draws the cached list with "N waiting to sync" (the data source falls back to its on-device snapshot). Logic lives in `src/widget/` (`widgetModel`, `widgetController`, `widgetState`, `widgetBridge`) and is unit-tested; only `ShoppingWidget.tsx` and the native rendering are device checks.

## D442 What the widget shows and what a tap does (P3-C)

Header "Shopping list" + "N to buy": tap opens the app. Up to 8 open items in the order the shopping screen uses (the selected store's aisle order when the phone has one selected, else the data source's category order), with a short quantity; "+N more in the app". Tap a row: ticks it (the row disappears). A footer "Ticked X. Tap to undo" stays for 2 minutes and while the item is still ticked (a misplaced tap on a small target is easy). Tapping a stale row is refused by the engine (nothing double counted) and the widget just refreshes. Light and dark layouts. Signed out: "Open Family Recipes and sign in".

## D443 Widget privacy and sign-out (P3-C)

The widget persists only the household id and the last ticked item (id, name, time). Sign-out, account deletion, leaving a household and a missing or expired session all clear it and draw the signed-out prompt, so a list never stays on the home screen after sign-out. The widget category is the home screen only (not the lock screen); item names are visible to anyone holding the unlocked phone, as with any widget (threat model WG1). Click payloads are untrusted: only a string item id (at most 64 characters) is used.

## D446 Offline web shopping list: same engine semantics, IndexedDB, one page cached (P3-C)

Queue: the web `ShoppingController` already used the engine's offline client model; its pending store moves from localStorage to IndexedDB (`lib/offline/shopping-store.ts`): same commands, client-generated ids, replay in order on reconnect (`online`, focus, poll), conflict toasts. It is bound to the signed-in user (another user never inherits or replays it), merges across tabs in one transaction (a tab only removes commands it acknowledged), migrates the old localStorage queue once, and falls back to localStorage where IndexedDB is missing. The last confirmed list (cursor, state, meta) is saved per list; a page served from the cache adopts a NEWER on-device snapshot of the same list (never goes backwards), then replays the queue over it. Service worker (`public/sw.js`, push handlers untouched): only GETs of `/shopping` (network first; the cached copy is used when the network fails, errors with 5xx, or takes longer than 6 s; redirects and non-HTML are never stored, so a signed-out visit cannot replace the list) and static assets (`/_next/static`, `/icons`, `/vendor`: hashed files cache-first, others network-first). The page asks the worker to keep the assets it already loaded ("warm"), because those loaded before the worker controlled the page. Everything else (APIs, server actions, other pages) is untouched; other pages answer a plain "You are offline" notice when the network fails. Privacy: the cached HTML contains the list, so the sign-in / sign-up / reset pages wipe the page cache and the snapshot (the queue is user-bound and kept for the same user); there is no Background Sync (not on Safari): replay happens while the page is open. Not offline: planner, recipes, pantry and every other screen. Banner: "You are offline ... N waiting".

## D447 Phone as a scanner: a short-lived capability, not a login (P3-C; implements the D275 design)

On `/pantry/scan` and `/receipts`, "Use my phone" starts a session: `scanner_session_create` (SECURITY DEFINER; the caller must be an active member of an active household) stores only the SHA-256 of a 256-bit random token, the household, the creating user, a purpose (`pantry` or `receipt`) and an expiry of at most 10 minutes; a new session revokes the user's previous one; at most 20 per user per hour. The QR code holds `<origin>/scan/phone?s=<id>#t=<token>`: the token is in the URL FRAGMENT (never sent to a server or in a Referer), and the phone page removes it from the address bar after reading it. The phone is NOT signed in: it holds the capability and can call exactly two functions, `scanner_connect` and `scanner_push` (granted to `anon`; the tables have no anon access at all). They check the token hash, expiry, revocation, that the creator is still an active member of an active household, and that this is THE scanner: the first phone to connect claims the session (its device id, hashed); any other gets `scanner_in_use` until the desktop presses "Use a different phone". Ten wrong tokens revoke a session; a wrong id and a wrong token answer identically. Caps: 120 pushes a minute and 300 items per session, 10 photos of at most 1.5 MB (JPEG, PNG or WebP only), idempotent per client id. The desktop user can revoke at any time ("Stop"; leaving the page also ends it), which deletes what the phone sent.

## D448 Phone clients: the web phone page and the Android app share one engine module (P3-C)

`@fr/engine/scanner` (pure): link build and parse, error codes and messages, rate limiter, and `PhoneSender`, the phone's retrying queue (a scan survives a bad connection and is resent with the SAME id; fatal errors stop with a message; a refused photo is dropped with a message while scanning carries on). Web phone page `/scan/phone` (public, no app navigation, `noindex`, `no-referrer`): camera barcode loop reusing the desktop decoder (platform detector or zxing-wasm), the same count-once-while-held rule, typed digits, photo from the camera (downscaled to 1600 px, then 1100 px, to fit 1.5 MB), a recent-sends list. Android: More > "Scan for a computer" reads the QR code with expo-camera, or opens straight from the `https://<host>/scan/phone` App Link (`app/scan/phone.tsx` reads the token from the full URL), or takes a pasted address. The app only accepts a link whose origin is the server it is configured for (`EXPO_PUBLIC_API_BASE_URL`), so a hostile QR code cannot redirect scans or photos elsewhere. Barcodes use `@fr/engine/pantry` `sight`; photos go through expo-image-manipulator (JPEG, base64). No sign-in is needed on the phone.

## D449 Desktop side, storage and cleanup (P3-C)

Tables `scanner_sessions`, `scanner_items` (small rows, in the Realtime publication) and `scanner_photos` (bytes kept apart so Realtime never ships them); RLS select only, for the creating user while still a member; every write is a function. The desktop hook (`useScannerSession`) polls `GET /api/scanner/sessions/<id>?after=<seq>` every 2 s (5 s once Realtime is confirmed) and applies each item exactly once, in order (`createApplied`); Supabase Realtime (INSERT on `scanner_items`, filtered by session) is only a hint that triggers the next read, so a missed event costs seconds and mock mode behaves the same. A phone barcode joins the same tally as the desktop camera (a new code through the same counting rule, extra units as +1); a phone photo joins the photos to scan (pantry) or becomes the receipt photo (receipts); the existing review and confirm are unchanged, so NOTHING is written to the pantry or receipts until the desktop user confirms. Photos are served only to the creating user (`no-store`, `nosniff`, image types only). The scheduled purge job also calls `scanner_purge_expired` (sessions an hour after expiry); the three tables are listed in the export's `EXCLUDED_TABLES` (credentials and transient data). Mock mode uses an in-memory store with the same rules (`MemoryScannerStore`); the SQL is the source of truth in production and has its own RLS script (`014_p3c_scanner_sessions.sql`). Not built: a phone-side queue that survives an app restart (sessions last 10 minutes), scanning for review flows other than pantry and receipts.
## D430 Nutrition goals are special category data: their own consent, own rows only, deleted on withdrawal (P3-B)

Per-person nutrition goals ("more fibre", "less salt"...) reveal health-related information, so under UK GDPR they need explicit consent (Art 9(2)(a)). New `consent_type` value `nutrition_goals` (migration `20261021003100`, separate from the allergy consent so withdrawing one never touches the other) recorded in `consent_records` with wording version `g1` (`GOALS_CONSENT` in `@fr/engine/nutrition`, shared verbatim by web and Android). Tables `nutrition_goal_profiles` (household, user, adult confirmation, portion share 0.25-2, `nudge_plan`) and `nutrition_goals` (goal id from a fixed list of six), migration `20261021003110`. RLS differs deliberately from soft dislikes (D378): **only the person** reads or writes their rows, not other members and not the household owner (a family owner cannot see a partner's goals). Writes need the household writable AND an active consent, checked in the policies and in `set_nutrition_goals()` (so a direct API call cannot bypass the UI); withdrawing the consent **deletes** the rows (trigger on `consent_records`, not just hides them); leaving a household or deleting an account deletes them (trigger on `household_members.status = 'left'`; household/account purge cascades). Opening the screen creates no data; saving goals without consent is refused and stores nothing, not even a consent record. Tests: `packages/db/tests/rls/014_p3b_nutrition_goals.sql`, `apps/web/lib/server/goals/goals.pglite.test.ts`.

## D431 Reference values are cited UK public guidance, read from the official pages on 2026-10-21 (P3-B)

Looked up with WebFetch and recorded in `GOAL_DEFS` (value, wording, page title, URL, the page's own "last reviewed" date), shown in the UI next to each goal with a link out. All are NHS pages for adults: fibre **30 g a day** (How to get more fibre into your diet, reviewed 2 March 2026, https://www.nhs.uk/live-well/eat-well/digestive-health/how-to-get-more-fibre-into-your-diet/); salt **no more than 6 g a day** (Salt: nutrition and healthy eating, 17 April 2023, https://www.nhs.uk/live-well/eat-well/food-types/salt-in-your-diet/); **free sugars** no more than **30 g a day** (How does sugar in our diet affect our health?, 19 May 2023, https://www.nhs.uk/live-well/eat-well/food-types/how-does-sugar-in-our-diet-affect-our-health/); fruit and veg **at least 5 portions a day**, a portion 80 g (Why 5 A Day?, 30 September 2026, https://www.nhs.uk/live-well/eat-well/5-a-day/why-5-a-day/); fish **at least 2 portions a week, one oily**, a portion about 140 g (Fish and shellfish: nutrition and healthy eating, 26 June 2026, https://www.nhs.uk/live-well/eat-well/food-types/fish-and-shellfish-nutrition/); red and processed meat: if you eat more than 90 g (cooked weight) a day cut down to **70 g a day** (Meat in your diet, 1 May 2024, https://www.nhs.uk/live-well/eat-well/food-types/meat-nutrition/). Honest limits are stored with each goal and shown: the data has **total** sugars, not free sugars (so it over-counts); the 70 g is cooked weight while recipe weights are raw (so it reads higher); table salt and snacks are not in recipes; tinned tuna is not oily fish. Reviewing a value later means changing one constant and its date. Two first-guess NHS URLs returned 404; the working addresses above came from NHS search results.

## D432 Adults only, six fixed goals, no calories or weights, nothing for children (P3-B)

The goal list is a closed set of six ids (`more_fibre`, `less_salt`, `less_sugar`, `more_fruit_veg`, `more_oily_fish`, `less_red_processed_meat`), enforced by a CHECK constraint and the zod schema; there is no free text, calorie, energy, weight, BMI, age or condition field anywhere (data minimisation), and a test asserts no goal id mentions weight or calories. The reference values are adult values, so a person must tick "I am 18 or over" when they first consent (`adult_confirmed_at`); `set_nutrition_goals()` refuses without it. Household members today are always people with an account (no non-login members exist on main: feature-detected, nothing to build) and there are no kid profiles yet (P3-A); the service has an `isChild` seam on `GoalsCaller` that returns `forbidden` for load, save and withdraw, so kids' mode can plug in without touching this lane. No goal ever sets a target for a child, a calorie target, or a weight-loss target.

## D433 How progress is worked out: portion share, day share, "at least" (P3-B)

`summariseGoals` (engine, pure) over planned (or cooked, when `recipe_cooked` has rows) recipe meals. Each meal counts the person's **portion share** of one recipe serving (0.5 / 1 / 1.5, default 1) times the recipe's per-serving figure from the existing nutrition engine (so unknown/unavailable values keep their D61 status). Daily goals use the average per planned day. Because the planner mostly plans dinners, comparing dinners with a whole day's guidance would always look low: the guidance is scaled by a stated convention of how much of a day each planned meal type represents (breakfast 25%, lunch 30%, dinner 35%, snack 10%, shown in the UI as `MEAL_SHARE_NOTE`). Statuses are words, not scores: at-least goals met >= 100% of the matching share, close >= 75%, otherwise "some way off"; limits met <= 100%, close <= 125%, otherwise "some way off". **Missing data never counts as zero**: meals with no nutrition for the nutrient, lines that could not be weighed, and unmatched ingredients make the amount a lower bound ("at least X"), and the status is only as strong as that allows: an at-least goal can be "in line" from a lower bound that already reaches the line, a limit can only be shown as passed, anything else is "Not enough data to say". The weekly oily-fish goal is "unclear" with fewer than five planned days. Hints ("this week's planned meals are on the low side for fibre. If you like, you could try X instead of Y") appear only for "some way off" on **fully known** data, at most two, with the swap chosen from saved recipes that fit the slot, have complete data and no household exclusion hit (no AI, no new substitution call: the existing library is the cheap source); the words "should", "must", "healthy", "deficient" are not used (tested). Every panel carries `GOALS_DISCLAIMER`: estimates, not medical or dietary advice, snacks/drinks/seasoning excluded, ask a GP or dietitian for health questions.

## D435 Per-recipe goal profile (P3-B)

Oily fish: salmon, mackerel, sardines, pilchards, herring, kippers, trout, whitebait, anchovies, eel, swordfish and fresh tuna, but not tinned tuna, fish sauce, stock or paste. ## D436 Planner nudge: opt-in, anonymous, soft (P3-B)

"Nudge meal plans towards my household's goals" is a per-person checkbox, **off by default**, stored as `nudge_plan`. The planner never reads goal tables: `planner_goal_nudge(household)` (security definer, caller must be a member) returns a deduplicated list of goal **ids** for members who have an active consent and opted in, with no user ids, names or counts. `loadPlanServices` sets `PlanServices.goalNudge`; `withGoalFit` computes a 0..1 `goalFit` per recipe (`recipeGoalFit`: average over the goals of how well one serving suits a dinner-sized share; unknown scores 0, never rewarded or penalised) and the solver subtracts `goalFit x 12` (new weight `goalFit`, same family as favourite 30 / dislike 20 / rating 8). It is a preference, never a filter: hard exclusions and diet/budget constraints still win, a poorly fitting recipe is still used when needed (tested), nothing changes when nobody opted in (identical plans, tested), and the report gains a non-hard "Nutrition goals" item saying how many planned meals suit the goals. In a one-person household the id list reveals that person's goals to themselves only; in larger households ids are pooled.

`apps/web/lib/server/goals/` (types, memory store for mock mode, Supabase store as the signed-in user, service) is used by the web server actions (`app/settings/goals-actions.ts`) and the bearer route `/api/goals` (GET own state; POST `save` / `withdraw`; 403 `CONSENT_REQUIRED`, 422 field errors, 403 `READ_ONLY` for saves while the household is pending deletion, withdraw always allowed because removing data is never blocked). ## D420 Shared family cookbook: a link, not a feature flag (P3-A)

A household shares one recipe or a named collection (favourites, quick, budget, vegetarian: resolved on the server to up to 50 recipes at that moment) with another household by a link `/s/<token>` (Android: `familyrecipes://s/<token>` and the https App Link path prefix `/s/`). ## D421 What a share exposes, and how a copy is made (P3-A)

Only a whitelisted view built field by field (`share_recipe_doc` in SQL, the same mapping in the memory store): title, description, times, servings, cuisine, tags, ingredient lines, steps, the cover photo and the ORIGINAL source attribution. Never notes, ratings, favourites, cooking history, versions or original page photos, nor any household or user id. "Save a copy" builds the recipient's recipe from exactly that view through the normal save path (ingredient linking included), credits the sharer ("Shared by Alice's household. Originally: ..."), copies the cover into the recipient's own storage (a new object; best effort, a recipe without its photo beats none) and records `recipes.source_share_id`. A household cannot save its own link.

## D422 Tokens, enumeration and rate limits (P3-A)

The token is 64 hex characters (two v4 UUIDs, ~244 bits), shown once; only sha256 is stored (like invitations). Every unknown, malformed, expired or revoked token answers the same (`NULL` from the RPC, `{kind:'invalid'}` from the service, one generic page / message), so nothing can be probed. Lookups are limited in process (60 per minute per user or address, 10 failed lookups per 10 minutes, 30 saves per hour, 30 links per hour); a second App Service instance would only double the allowance, and the token entropy is the real defence. Per-household cap of 200 active links.

## D423 Signed-out visitors and photos (P3-A)

Signed out, a link shows a minimal preview (title, "Shared by X's household", how many recipes) and a sign-in prompt that returns to the link (Android keeps it for an hour, like invitations). The sharer can tick "readable without signing in" (off by default): then the recipes show as text only, with no recipient row and no photos, because Storage stays private. Photos reach a signed-in recipient through a storage policy (`share_image_visible`) that allows only the cover objects of a LIVE share the person opened, and through `/api/shares/<token>/image/<recipeId>` (a 2-minute signed URL minted by the caller's own client). No service-role key is involved (D100). Revoking or expiry closes it at once.

## D424 Deletion, export and the sharer's view (P3-A)

## D426 Rounds and votes (P3-A)

## D427 Kids' screen and the parent PIN (P3-A)

`/kids/play` (web, no app navigation) and `kids-play` (Android, headerless, gestures off, hardware Back swallowed) show big pictures with two big buttons and no text input at all. The PIN is a speed bump for a child, not a security boundary against someone holding the unlocked device; a web page cannot lock the browser itself (Back is held best effort), which is why the Android screen goes further.

## D428 Results feed the planner softly (P3-A)

A CLOSED round overlapping the plan's dates gives the planner its liked recipes (best score first) through a new orchestrator dependency `votes`: they become the favourites of one extra pseudo-member "Family vote", so the existing soft favourite weight applies and allergies, exclusions, budget and variety still win (tests: an open round changes nothing, a closed one pulls the recipe in, an excluded ingredient still wins).
