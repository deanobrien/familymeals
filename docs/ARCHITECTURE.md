# ARCHITECTURE.md

How the system is put together as built (not as originally planned; for that see [product/BRIEF.md](product/BRIEF.md)). Reasons for each choice are in [../DECISIONS.md](../DECISIONS.md); `D<n>` below refers to it.

## 1. Workspace

pnpm workspace + Turborepo, scope `@fr/*`, packages export TS source with no emit (`main: src/index.ts`; D3), `apps/web` consumes them through `transpilePackages`. A package's `build` script is a `tsc` type-check only. Root `pnpm.overrides` pin zod 4, TypeScript 5.7, vitest 2, React 19 (D8).

| Path | Package | Role |

## 2. Web app internals

Server-only code lives in `apps/web/lib/server/**` (refdata catalogue `refdata/catalogue.ts` D28; `calc/` per-household cost and nutrition calculators D60-D64, D100-D101; `prices/store.ts`; `plan/`; `shopping/`; `receipts/`; `pantry/`; `import/`; `ai/` provider resolution + encrypted settings; `supabase/` repositories; `config/production.ts`; `auth/`; `uploads/`). Route handlers: `app/api/{extract,pantry/scan,uploads,health,dev}`. Pages: `/` (home), `/recipes`, `/plan`, `/shopping`, `/settings/stores`, `/receipts`, `/pantry` (+ `/pantry/scan`), `/household`, `/settings`, `/privacy`, auth routes, `/invite`.

Every request is scoped by `getAppContext()` (`lib/server/context.ts`, D35): the signed-in user and active household. Without Supabase env, mock auth gives "Alice Smith / household A" (bannered); in dev an `fr_household=e2e-*` cookie selects a sandbox household for tests. In production mock auth is refused.

### Backend selection (`lib/server/supabase/backend.ts`)

```
DATA_BACKEND=supabase  AND  NEXT_PUBLIC_SUPABASE_URL + NEXT_PUBLIC_SUPABASE_ANON_KEY   -> Supabase repositories
anything else                                                                           -> in-memory repositories
```

Supabase repositories run **as the signed-in user** with a user-scoped client, so RLS applies; there is no service role on the request path (D100). Each store has an interface with an in-memory and a Supabase implementation: recipes (`RecipeRepository`), plans (`MealPlanRepository`, `PlanRecipeSource`), pantry (`PantryRepository`, `PurchaseEventSource`), shopping (`ShoppingRepository`), receipts (`ReceiptRepository`), prices (`PriceStore`), planner household profile, AI settings (`AiSettingsStore`). Multi-table writes go through SECURITY DEFINER RPCs (D51). Production start refuses: mock auth, mock AI, in-memory backend, missing/weak `APP_SECRET`, local file store unless `ALLOW_LOCAL_FILE_STORE=true`, and the dev service-context fallback (D150, `lib/server/config/production.ts`).

### AI provider selection (`lib/server/ai/provider.ts`)

`resolveAi()` precedence: household Settings (owner-saved, key encrypted AES-256-GCM with `APP_SECRET`, D41/D126) > environment (`AI_PROVIDER` + `ANTHROPIC_API_KEY` / `OPENAI_API_KEY`) > dev default **mock**. A real provider with a missing key reports "not configured"; it never silently falls back to the mock. The mock returns canned, deterministic data and is used by all tests and CI.

## 3. Data flows

**Photo -> AI -> draft -> review -> recipe.** Browser (or Android) uploads photos to `/api/extract` (images downscaled in the browser; >10 MB handled) -> `@fr/ai` `extractRecipe` (multi-page, rotation, bracket quantities, printed nutrition/allergens) -> `@fr/recipe-import` draft -> engine `parse` + `normalise` match lines against the refdata catalogue -> review screen with confidence flags and corrections -> `/api/extract/save` finalises through the household's RecipeSink (Supabase repository when configured). Original extraction and corrected content are kept as `recipe_versions`. Cost and nutrition are derived on read, never stored (D63).

**Plan prompt -> constraints -> solver -> approve -> shopping.** `/plan` prompt -> `parsePlanPrompt` -> a `PlanRequest` subset of `PlanConstraints` (D130-D131) -> exclusions resolved to ingredient ids / UK-14 allergen groups (D132) -> editable constraint chips (D133, no second AI call) -> `@fr/engine/planner` solver via `lib/server/plan/engine-solver.ts` (quick meals soft-strong or hard-strict, D134; cost and weekly nutrition computed) -> proposal -> user approves -> the **approved** plan generates the shopping list through `@fr/engine/aggregate` (D33).

**Shopping (shared, real-time).** The list is state in `@fr/engine/shopping`; clients send commands (tick, purchase, void, ...) with ids; with Supabase the engine decides over a consistent snapshot and `apply_shopping_command` / `record_purchase` / `void_purchase` persist under a head check, logging every outcome in `shopping_command_log` with a per-list `list_seq` cursor (D120-D121). Realtime INSERT events are only a hint to refetch by cursor (D122); mock mode polls every 4 s.

**Stores and aisle order (AS1, D290-D299).** `stores` / `store_aisles` / `store_placements` are household data under RLS (`StoreBookRepository`: in-memory and Supabase, one shared contract suite). `@fr/engine/shopping` `orderForStore` is pure: ingredient > item-name > category placement, unplaced items last in "Not placed yet"; `suggestRouteOrder` backs the suggest-only "learn from my route". `/shopping` loads the whole `StoreBook` once (`household_store_book`), orders on the client (so it works offline, cached in localStorage; offline placement edits are queued and replayed), and `/settings/stores` edits it through server actions (`app/shopping/store-actions.ts`). Android reads the same RPC (cached in AsyncStorage).

**Receipts -> matcher -> purchases -> prices.** Photo -> `parseReceipt` -> `@fr/engine/receipt-match` against the outstanding shopping list (deterministic matcher first; AI only ranks uncertain lines) -> user confirms -> confirmed lines tick/purchase items; "extra" lines go to the pantry service (D103); receipt prices are recorded as household price observations (`ingredient_prices`, D124) and rank above generic estimates in the `@fr/engine/cost` basket estimate (D34, D101).

**Continuous barcode scan (BS1, D270-D276).** `/pantry/scan` > "Scan barcodes continuously": camera -> frame loop (`lib/products/scan-loop.ts`, centred downscaled region, ~10 fps) -> decoder (`lib/products/decoder.ts`: platform BarcodeDetector when it reads EAN-13, else lazy zxing-wasm self-hosted at `public/vendor/zxing`) -> normalised retail code -> tally (`@fr/engine/pantry` `rapid-scan.ts`: debounce, re-scan, undo, snapshot) -> background lookups through `POST /api/products` (`lib/server/products/batch.ts`: household snapshots, LRU, per-household round-robin queue behind the Open Food Facts limit; the client polls pending codes) -> Done opens the same review step (pending rows block confirm, unknown rows need a name). The session lives in `ScanFlow` (`use-rapid-session.ts`), so lookups keep resolving during review. Android (`RapidBarcodeScan`) shares the engine logic and hands its tally to the web via `?mode=rapid&codes=`.

**Handwritten list scan (SL1, D260-D267).** `/shopping/scan` -> `POST /api/shopping/scan` (read-only; cookie or bearer) -> `scanShoppingList` (`packages/ai/src/shopping-list-scan.ts`: transcription + parsed quantity only when written, crossed-out / illegible flags; sanitised in code) -> `lib/server/shopping/list-scan.ts` maps rows through the catalogue matcher -> review in the browser -> `previewShoppingScanAction` / `confirmShoppingScanAction` (`list-scan-apply.ts`: one planner simulates the engine's `add_item` / `edit_item` over the destination list, so preview = confirm; command ids derived from household + batch id + row key = idempotent). Several lists per household, one active: `ShoppingRepository.createList / activateList / renameList / archiveActiveList`, SQL `shopping_list_create` / `shopping_list_activate`; `ListMeta.listId` + the list-id guard in `syncList` keep a client from mixing lists.

**Pantry scan.** `/pantry/scan`: video turned into 6-10 sharp JPEG frames in the browser (D82), only JPEG frames uploaded -> `scanPantry` (items, counts, pack sizes, UK use-by vs best-before, close-up flag; output sanitised in code, D81) -> review with the engine's conservative matcher, editable quantities/dates, close-up re-scan merges dates only (D88), opt-in labelled shelf-life estimates (D87), merge-with-stock preview -> **nothing written until confirm** (D84).

## 4. Provider interfaces

- **AI** (`packages/ai/src/provider.ts`): `AiProvider` = `extractRecipe`, `parseReceipt`, `suggestTags`, `parsePlanPrompt`, `suggestIngredientMatches`, `suggestSubstitutions`, `scanPantry`. Config kinds: `mock | openai | azure | anthropic` (`packages/ai/src/config.ts`). Usage/cost metadata via `usage.ts`; strict JSON schemas via `strict-schema.ts`.
- **Prices**: `PriceStore` (`lib/server/prices/store.ts`): refdata generic estimates + household receipt/user prices; hierarchy encoded in `price_kind` (SCHEMA.md).
- **Recipe sources**: the library and planner read recipes through `RecipeRepository` / `PlanRecipeSource`. External recipe discovery (TheMealDB, lane X1) is being added as another source behind the same kind of interface; check `DECISIONS.md` blocks above D155 and `docs/ROADMAP.md` for what landed.
- **Product sources**: pack sizes / barcodes from Open Food Facts (lane X2) are being added as a product source; same note.
- **Nutrition**: CoFID via `@fr/refdata`, value status `known | zero | unknown | unavailable`, never presenting unknown as zero (D61).
