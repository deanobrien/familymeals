# SUPABASE.md

Supabase provides Postgres, Row Level Security, Auth, Realtime and Storage. The CLI is a devDependency: always run it as `pnpm exec supabase ...` from the repo root. Config and migrations are in `supabase/` (D4). The schema, RLS model and RPC list are in [../supabase/SCHEMA.md](../supabase/SCHEMA.md); read that before changing a migration.

## 1. Local stack (Docker)

Requires Docker running. Docker 20.10.7 works (LV1) because `supabase/config.toml` disables `edge_runtime` and analytics (the edge container exits 255 on 20.10). Verified 2026-10-19: all 23 migrations plus the seed apply cleanly on Postgres 17.11.

```
pnpm exec supabase start            # first run pulls images and applies every migration + supabase/seed.sql; prints API URL, anon key, service_role key
pnpm exec supabase status           # reprint the URLs and keys later
pnpm exec supabase db reset         # drop and re-apply supabase/migrations/* (+ seed if any)
pnpm exec supabase stop
```

Ports (from `supabase/config.toml`; shifted to 554xx because another local Supabase project, golfbook, owns 543xx: never stop its containers): API 55421, DB 55422, Studio 55423, Mailpit mail catcher 55424 (http://127.0.0.1:55424). The printed keys are well-known local development keys, not secrets, but still do not paste them into docs.

Easiest: `pnpm dev:live` runs the app on http://localhost:3131 against the stack with the right env (D142); `pnpm test:e2e:live` runs the live suite (D143, TESTING.md). `supabase/seed.sql` (reference ingredients) is generated by `pnpm --filter @fr/refdata build:sql-seed` (D145). To run the normal dev server against it instead, create `apps/web/.env.local` (git-ignored; Next reads `.env*` from `apps/web/`, not the repo root):

```
DATA_BACKEND=supabase
NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:55421
NEXT_PUBLIC_SUPABASE_ANON_KEY=<anon key from supabase status>
NEXT_PUBLIC_SITE_URL=http://localhost:3100
```

then `pnpm dev`. Notes:

- Local Auth mirrors the hosted settings: email confirmation ON (the confirmation link arrives in Mailpit), minimum password length 10. Check the `[auth]` URLs in `supabase/config.toml` match the port you use; for `pnpm dev` (3100) against the stack, `http://localhost:3100/auth/callback` must be in `additional_redirect_urls` (then `supabase stop` / `start`).
- No service-role key is needed on the normal path (D100). Only set `SUPABASE_SERVICE_ROLE_KEY` if you exercise the admin-client paths (`apps/web/lib/server/auth/admin.ts`).
- LV1 ran the app and a 20-test live suite on this stack (D140-D149) and found three bugs, fixed by migrations `20261019001910_lv1_invitation_email_lock.sql` (invitations locked to the invited email), `20261019001920_lv1_pantry_source_values.sql` (`pantry_source` enum values) and the generated seed.
- **Pushing to the hosted project (owner)**: `pnpm exec supabase link --project-ref guzsjqoosjqxfuqrjhxu`, then `pnpm exec supabase db push --include-seed` (`--include-seed` is required: it loads the reference ingredient list).

## 2. Migrations

Files are `supabase/migrations/<14-digit timestamp>_<name>.sql`, applied in filename order. All are `20261019...`:

| Timestamp prefix | Name | What |
|---|---|---|
| 000000 | baseline_extensions | extensions baseline (pgcrypto) |
| 000100 - 001100 | foundation, households, reference_data, recipes, meal_planning, shopping, receipts_pantry, nutrition_ai, rls, storage, realtime | schema v1 (L1), RLS on every table, private storage buckets, Realtime publication |
| 001200 | privacy_lifecycle | consent, deletion grace period, purge (L24) |
| 001300 | shopping_commands | `record_purchase` / `void_purchase`, command log |
| 001400 | owner_decisions | decisions A-D (D21-D24) |
| 001500 | transfer_ownership | atomic owner swap RPC (D37) |
| 001520 | recipe_plan_pantry_repositories | S1 repository RPCs (D51) |
| 001540 | pantry_purchase_mode_source_of_truth | D104 |
| 001600 | shopping_repository | S2: engine item state, `list_seq` cursor, `apply_shopping_command` |
| 001610 | receipts_prices | S2: `save_receipt`, price observations |
| 001620 | household_profile_ai_settings | S2: planner profile, per-household AI settings (ciphertext) |

Rules for adding one: new file with a later timestamp, never edit an applied migration once it has been pushed to the cloud project; keep every table RLS-enabled (a test asserts it); add SQL assert scripts under `packages/db/tests/rls/` and run `pnpm --filter @fr/db test` (applies **every** migration to in-process Postgres via PGlite, then runs the RLS scripts). Note PGlite has single-connection limits (no true concurrency), so concurrency semantics need the live stack.

## 4. Realtime

Migration `...001100_realtime.sql` adds `shopping_lists`, `shopping_list_items`, `purchase_events`, `meal_plans`, `planned_meals`, `pantry_items` to the `supabase_realtime` publication, and `...001300_shopping_commands.sql` adds `shopping_command_log` (both guarded: no-ops if the publication does not exist). The app uses Realtime as a **hint** (D122, `apps/web/lib/shopping/live.ts`): the browser subscribes to `shopping_command_log` INSERTs filtered by `household_id` and then fetches by per-list `list_seq`; it polls only while the channel is down. After a push, confirm in Dashboard > Database > Replication that these tables are in the publication (the local publication was verified in LV1).

## 6. Storage

Private buckets `recipe-images` and `receipt-images` (10 MiB limit; jpeg/png/webp/heic), created by migration `...001000_storage.sql`; `db push` is the whole cloud setup (afterwards Dashboard > Storage should show both as **Private**; never add public policies). Access = active membership of the household named by the first path segment (select / insert / update / delete policies; owner-decision write locks for pending-deletion households apply).

**Used by the web app since ST1 (D190-D196).** Object paths `<household_id>/<kind>/<id>/<file>`:

| Bucket | Path | Holds | Lifetime |
|---|---|---|---|
| `recipe-images` | `<hh>/page/<uploadId>/page-N.jpg` | photo pages of a recipe import (review-screen previews, source of the cover) | deleted when the recipe is saved; abandoned ones after 24 h (cleanup job) |
| `recipe-images` | `<hh>/cover/<uploadId>/cover.jpg` | the recipe's cover (`recipes.cover_image_path`; the recipe's `imageUrl` IS this path) | until the recipe is deleted (archived) or the cover is replaced |
| `receipt-images` | `<hh>/receipt/<receiptId>/receipt.jpg` | the receipt photo (`receipts.image_paths`) | 90 days after confirmation, or when the receipt / household is deleted |

Code: `apps/web/lib/server/images/` (`ImageStore` interface; `LocalImageStore` for dev / mock mode; `SupabaseImageStore` through the caller's own client; `paths.ts` for the path rules and `imageSrc()`; `cleanup.ts`). Browsers never get a public URL: components render `/api/images/<path>` (`imageSrc()`), and `app/api/images/[...path]/route.ts` checks the session (cookie or Android bearer token), the household in the path and Storage RLS, then 302s to a 5-minute signed URL. Another household's or a missing object is a 404. During import the review screen's previews use `/api/uploads/<id>/<file>`, which does the same in Supabase mode.

Cleanup: `storage_cleanup_queue` is filled by DB triggers (recipe / receipt / image-row deletes, cover replacement, **recipe archive** which releases the cover, household purge) and by `enqueue_stale_uploads()` / `purge_old_receipt_images()`; it never queues an object a live row still references (a duplicated recipe shares its cover). `POST /api/jobs/storage-cleanup` (header `x-cron-secret`) runs all three and deletes the objects through the Storage API; scheduling is in [DEPLOY-APP-SERVICE.md](DEPLOY-APP-SERVICE.md) section 4b. Migration: `20261020002100_st1_storage_uploads.sql`.

## 7. Generating types

`packages/db/src/database.types.ts` is a placeholder (the hand-written zod row schemas in `@fr/domain` are the typed contract). To generate real types:

```
pnpm exec supabase gen types typescript --local > packages/db/src/database.types.ts
# or, against the cloud project:
pnpm exec supabase gen types typescript --project-id guzsjqoosjqxfuqrjhxu > packages/db/src/database.types.ts
```

then run typecheck: the placeholder's empty `Database` interface is replaced, so downstream imports may need small fixes.

## 8. RLS model summary

RLS is enabled on every table; `anon` has no grants; helper functions `is_household_member()` / `is_household_owner()` (SECURITY DEFINER, empty search_path) are used by all policies; household-scoped rows carry `household_id` with composite foreign keys so a row can never point at another household's parent; purchases, receipts and the shopping command log are written only through SECURITY DEFINER RPCs; reference data is read-only to clients; a deleted household is read-only for a 14-day grace period (D24). Full detail: [../supabase/SCHEMA.md](../supabase/SCHEMA.md) sections "Key design decisions" and "RLS model".
